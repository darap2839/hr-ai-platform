# Проверка доступа API после включения Keycloak Bearer

Все HTTP `/api/*` защищены, кроме явного списка bootstrap/callback URL входа.
`/health` остаётся доступным для диагностики и контейнерных healthcheck.
Анонимный запрос к кадровым данным/документам возвращает 401 до обращения к БД.
`user_login`, mock-token и query token на CRUD не принимаются.

Проверяются RS256-подпись через доверенный JWKS, exp/iat/iss/sub, тип Bearer и
azp текущего clientId. Ключи загружаются по внутреннему адресу Keycloak с
кешированием и обновлением при смене kid. Адрес ключей не берётся из токена.
При сетевой недоступности JWKS — 503, без перехода на локальный HMAC-secret.
При неверном/истёкшем токене — 401. Ответы защищённого API — private, no-store.

Настройки, не требующие изменения существующего Compose:

| Переменная | Значение по умолчанию/назначение |
|---|---|
| KEYCLOAK_URL | Существующий внешний адрес провайдера, тот же, что получает keycloak-js |
| KEYCLOAK_REALM / KEYCLOAK_CLIENT_ID | Существующие realm/client |
| KEYCLOAK_INTERNAL_URL | http://keycloak:8080/auth, только получение ключей |
| KEYCLOAK_ISSUER | KEYCLOAK_URL/realms/KEYCLOAK_REALM; явное значение при фиксированном issuer |
| KEYCLOAK_JWKS_URL | Необязательный доверенный адрес ключей; без токен-зависимого discovery |
| KEYCLOAK_AUDIENCE | Если задана, дополнительно строго проверяется aud |

Существующий импорт realm не настраивает audience платформы в access token;
для совместимости привязка к клиенту проверяется через подписанный azp, тип
Bearer и issuer. Это отличается от проверки выделенной API audience. При
введении отдельного API client/audience требуется соответствующая настройка
realm и KEYCLOAK_AUDIENCE, а не отключение проверки подписи.

Существующий EventSource передаёт access token в query. Это допускается только
для точного `/api/sse/notifications`, с той же криптографической проверкой.
Маршрут включён под `/api`, пользователь берётся из проверенного sub.
Доставка и маршрутизация событий в браузере требуют отдельного испытания;
проверка допуска к потоку не означает прохождение этих испытаний.

Frontend сохраняет Bearer при пользовательских headers, обновляет токен раз
в 30 секунд при остатке менее 70 секунд, передаёт новый токен SSE-клиенту,
очищает токен/таймер/поток при выходе. Шапка и Sidebar показывают текущие
name/username, а не демонстрационный профиль.

## Применение и проверка

Не обновлять backend до успешной публикации конкретного образа. Для полной
проверки требуется также обновлённый frontend, затем новый вход в браузере.
Роль/разрешения по подразделениям этой проверкой не реализуются.

После установки: анонимный GET /api/candidates должен дать 401; вход в
браузере должен сохранить доступ к вакансиям/кандидатам/документам. Далее
проверяются обновление токена и выход. Если реальный подписанный токен
отклоняется, сначала сравнить доверенные issuer/client/JWKS с конфигурацией
Keycloak; не включать обход проверки.

Ранее выданный functional-diagnostics.py выполняет CRUD без токена. После
этого изменения его 401 на CRUD ожидаемы: старый прогон нельзя использовать
как проверку авторизованного CRUD. Успешные функциональные проверки до
включения защиты сохраняются как отдельные доказательства. Новый
авторизованный прогон требует токена, полученного штатным входом; токены и
пароли не следует включать в ZIP, URL общего API либо публиковать в PR.
