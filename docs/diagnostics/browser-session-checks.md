# Проверки браузерной сессии на локальном стенде

Адрес приложения: http://127.0.0.1:18080. Вход выполняется под существующим
admin; ожидаемое отображение в приложении — Дарья Попова / depopova.
Профиль на панели не доказывает, что сервер принял авторизацию.

Испытания выполняются на установленной версии. Исправление в PR, успешный
модульный тест и успешная публикация образа отмечаются отдельно от live-проверки.
Не запускать repair-local-login.ps1; настройки Keycloak для этих проверок не менять.

## Последовательность без изменения кадровых данных

1. Открыть Network в инструментах разработчика, включить Preserve log и очистить
   список. После входа открыть «Кандидаты». Найти запрос /api/candidates:
   ожидается 200 и отображение списка. Пустой список допустим.
2. Обновить страницу. Ожидается сохранение доступа и повторный успешный запрос
   /api/candidates. Отсутствие повторного запроса пароля при действующей сессии
   Keycloak допустимо.
3. Оставить вкладку активной и в Network отфильтровать token. Дождаться запроса
   обновления токена: POST .../protocol/openid-connect/token, grant_type=refresh_token.
   Ожидается 200. Время зависит от срока токена действующего realm; период таймера
   frontend 30 секунд не означает выдачу нового токена каждые 30 секунд.
   После этого ещё раз открыть «Кандидаты»: ожидается 200.
4. В Network найти /api/sse/notifications. Ожидается соединение 200,
   text/event-stream и событие heartbeat примерно каждые 15 секунд. Pending
   у открытого потока допустим. Heartbeat подтверждает транспорт, но ещё не
   доставку уведомления о кадровом действии.
5. Нажать «Выйти». Ожидается закрытие старого SSE и отсутствие новых подключений
   от старой страницы после выхода. Повторный вход должен снова открывать приложение.
   При сохранившейся серверной SSO-сессии отсутствие формы само по себе не является
   обходом защиты; отдельно фиксируются завершение сессии Keycloak и очистка клиента.

Достаточно сообщить статусы: кандидаты до/после обновления страницы, refresh,
кандидаты после refresh, heartbeat, выход и повторный вход. Не передавать значения
access/refresh token, cookie, пароль или полный URL SSE. HAR без очистки содержит
секреты, для этих проверок он не нужен.

## Обнаруженные ограничения уведомлений

Статический просмотр кода обнаружил отдельную проблему маршрутизации:
NotificationService отправляет событие только при заполненном _current_user_id,
но вызовов set_current_user в приложении не найдено. Кроме того, синхронный
обработчик, создающий уведомление, может выполняться без asyncio event loop,
а сервис в этом случае пропускает отправку. Это причины для отдельного
воспроизводимого интеграционного теста; heartbeat не закрывает этот дефект.

Единый mutable current_user в singleton нельзя просто устанавливать для каждого
запроса: одновременные запросы смогут подменять адресата. Решение требует явного
получателя события и проверки изоляции параллельных сессий. Роли и доступ по
подразделениям этой диагностикой не вводятся.
