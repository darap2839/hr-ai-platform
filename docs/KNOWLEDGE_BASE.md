# База знаний: продуктовая и UX-спецификация

Статус: согласовано для поэтапной реализации  
Версия: 0.1

## Цель

Вкладка «База знаний» должна быть самостоятельным рабочим инструментом для поиска и чтения корпоративных документов, создания внутренних страниц, загрузки файлов, работы с черновиками, публикации, архивирования, управления доступом и связывания документов с HR-сущностями.

Система должна оставаться полностью полезной без AI.

## Границы первого этапа

В первый этап входят:

- поиск и фильтрация документов;
- отдельные режимы чтения и редактирования;
- создание страницы без обязательного файла;
- загрузка PDF, DOCX и TXT с проверкой извлечённого текста;
- статусы `draft → published → archived`;
- мягкое удаление и восстановление;
- разделы, версии, владельцы и права доступа;
- связи с отделами, должностями и вакансиями;
- полнотекстовый поиск PostgreSQL.

В первый этап не входят:

- AI-генерация и AI-summary;
- ответы AI на вопросы;
- embeddings и обязательная интеграция с Qdrant;
- автоматическая классификация;
- LLM-рекомендации документов.

## Принятые продуктовые решения

1. Основное представление — таблица, сетка остаётся дополнительным видом.
2. Клик по документу открывает preview, а не редактор.
3. Просмотр и редактирование разделены.
4. Документ может существовать без исходного файла.
5. «Создать страницу» и «Загрузить файл» — разные действия.
6. Фильтры и поисковый запрос сохраняются в URL.
7. Удаление мягкое и обратимое; файл не удаляется немедленно.
8. Права вычисляются и проверяются backend.
9. API базы знаний версионируется через `/api/v1/knowledge`.
10. Поиск сначала реализуется средствами PostgreSQL.
11. Список документов всегда возвращает единый envelope.

## Роли

### Читатель

Видит доступные опубликованные документы, ищет, фильтрует, открывает, скачивает разрешённые файлы и работает с избранным.

### Редактор

Создаёт страницы, загружает файлы, редактирует свои черновики, отправляет документы на публикацию и архивирует их в рамках политики доступа.

### Владелец раздела

Управляет документами раздела, публикацией, возвратом в черновик, архивом, восстановлением, владельцами и доступом.

### Администратор

Видит все документы, управляет разделами и permissions, восстанавливает удалённые документы, просматривает журнал действий и обслуживает поисковый индекс.

Frontend скрывает недоступные действия для удобства, но backend повторно проверяет каждое действие.

## Основные сценарии

### Поиск и чтение

Поиск выполняется с debounce 300–400 мс. Результат открывается одним кликом в preview drawer. Пользователь может перейти на полную страницу документа.

### Фильтрация

Поддерживаются тип, раздел, отдел, статус, автор, владелец, наличие файла и избранное. Активные фильтры показываются chips и отражаются в URL.

Пример:

```text
/knowledge-base?q=отпуск&type=policy&department=HR&status=published
```

### Создание страницы

Отдельный editor route позволяет создать документ без файла, заполнить содержание и метаданные, сохранить черновик и позднее опубликовать.

### Загрузка файла

Пользователь выбирает PDF, DOCX или TXT, видит имя, размер, тип, прогресс и результат извлечения. Название, метаданные и извлечённый текст можно проверить до сохранения черновика.

### Редактирование и версии

Редактирование открывается с полной страницы документа. Каждое сохранение создаёт новую версию с автором, временем и кратким описанием изменений. Конкурентное изменение возвращает `412 Precondition Failed`.

### Публикация

Backend проверяет обязательные поля и permission. После публикации записываются `published_at` и actor.

### Архивирование

Архивный документ исчезает из обычного поиска, остаётся доступным по прямой ссылке авторизованным пользователям и может быть восстановлен. Восстановление переводит его в черновик.

### Удаление

Удаление заполняет `deleted_at` и `deleted_by`. Файл сохраняется до отдельной процедуры очистки. Восстановление доступно владельцу раздела или администратору.


## Основной экран

Экран содержит:

- заголовок и действия «Создать страницу» / «Загрузить файл»;
- строку поиска;
- левую навигацию;
- быстрые представления «Все», «Мои», «Избранное», «Черновики»;
- фильтры и chips;
- переключатель «Таблица» / «Сетка»;
- таблицу результатов и пагинацию.

Колонки таблицы по умолчанию: название, тип, раздел, автор, статус, последнее изменение и действия. Отдел является опциональной колонкой.

Без поискового запроса сортировка — `updated_at desc`; с запросом — по relevance.

## Preview drawer

Preview показывает название, статус, версию, раздел, автора последнего изменения, описание, содержание, связи и исходный файл.

Основные действия:

- открыть полностью;
- скачать файл, если он существует.

Дополнительные действия зависят от permissions:

- редактировать;
- опубликовать;
- скопировать ссылку;
- добавить в избранное;
- создать копию;
- архивировать;
- удалить.

## Состояния интерфейса

- Загрузка: skeleton таблицы.
- Пустая база: объяснение и действия создания/загрузки.
- Нет результатов: поисковый запрос, рекомендации и сброс фильтров.
- Ошибка: отдельное error state с повторной загрузкой; ошибка не маскируется под пустой список.

## Жизненный цикл

```text
draft     → published | archived | deleted
published → draft | archived | deleted
archived  → draft | deleted
deleted   → draft
```

Запрещены прямые переходы `archived → published`, `deleted → published`, публикация без названия/содержания и публикация без permission.

## Критерии готовности UX-этапа

- Документ находится поиском и открывается одним кликом из результата.
- Просмотр не включает режим редактирования автоматически.
- Состояние поиска и фильтров восстанавливается из URL.
- Все loading, empty и error states визуально различимы.
- Недоступные действия не показываются, а backend всё равно проверяет права.
- Документ без файла можно создать, прочитать, отредактировать и опубликовать.
- Архивирование и удаление — разные обратимые операции.
